# 后端答辩与压测说明

## 1. 当前后端架构

```text
前端用户
   |
   v
HTTP / WebSocket
   |
   v
后端实例 A / B / C
   |                \
   |                 \__ 本机内存：连接对象、短期缓存、演示态回退
   |
   +---- Redis：共享实时状态
   |       - 当前场次状态
   |       - 当前价 / 领先人 / 参与人数
   |       - 排行榜
   |       - requestId 去重
   |       - 结算租约
   |       - 房间事件流
   |
   +---- MySQL：正式业务账本
           - bids
           - auction_sessions
           - auction_results
           - auction_orders
```

## 2. 现在可以怎么讲

- MySQL 是正式账本，`bid/session/result/order` 默认要求持久化成功。
- Redis 是共享实时状态中心，负责原子出价、场次热状态、排行榜、结算租约和房间事件流。
- 本机内存不再承担全局唯一真相，主要用于连接管理、短期缓存和演示态回退。
- 多实例下，同一场次的结算通过 Redis 租约抢占，避免重复结算。
- 多实例下，WebSocket 广播通过 Redis 事件流同步，各实例只负责推送自己本机的连接。

## 3. 压测前准备

1. 确保 `MYSQL_DSN`、`REDIS_ADDR` 已配置。
2. 默认 `REQUIRE_PERSISTENT_LEDGER=true`，如果 MySQL 不可用，服务会直接启动失败。
3. 重置演示数据：

```powershell
.\Backend\scripts\reset_demo_data.ps1
```

4. 启动后端：

```powershell
go run ./Backend/cmd/server
```

5. 查看健康检查：

```text
GET /health
```

重点关注：

- `persistentLedgerRequired=true`
- `mysqlConfigured=true`

## 4. 基础压测命令

Windows PowerShell：

```powershell
.\Backend\scripts\load_bid_test.ps1 `
  -BaseUrl http://127.0.0.1:8080 `
  -Mode single `
  -Concurrency 20 `
  -RequestsPerWorker 30 `
  -CheckHealth `
  -SnapshotMetrics
```

脚本会输出：

- 总请求数
- 成功数
- 失败数
- `/health` 中的持久化状态
- `/metrics` 中的关键指标快照

## 5. 关键指标怎么讲

重点看这些 Prometheus 指标：

- `auction_bid_requests_total`
- `auction_bid_success_total`
- `auction_bid_failure_total`
- `auction_settlements_total`
- `auction_settlement_delay_ms_total`
- `auction_ws_connections_opened_total`
- `auction_ws_connections_closed_total`
- `auction_ws_active_connections`
- `auction_errors_total{type="..."}`

讲法建议：

- `bid_requests_total` 体现压测期间总出价请求规模。
- `bid_success_total / bid_failure_total` 体现成功率和失败原因分布。
- `settlements_total` 体现到期场次的结算完成情况。
- `settlement_delay_ms_total` 体现调度结算延迟。
- `ws_active_connections` 体现在线连接规模。
- `errors_total` 用于说明是否出现租约、广播或业务异常。

## 6. 一致性验证点

压测或演示后，建议检查：

1. 同一场次没有重复订单。
2. 同一场次只有一条最终结果。
3. 同一个 `requestId` 不会重复记账。
4. 排行榜最高价和当前场次当前价一致。
5. `/health` 显示正式账本模式已开启。
6. `/metrics` 中没有明显异常错误激增。

## 7. 这次架构强化后，和之前的区别

之前：

- MySQL 是“能连上就用，连不上就退回内存”
- 结算扫描主要依赖单机内存
- WebSocket 广播主要面向单机连接

现在：

- 默认要求 MySQL 可用，核心业务账本不再默默退回内存
- 结算通过 Redis 场次租约减少多实例重复执行
- 广播通过 Redis 事件流做跨实例同步

## 8. 仍需诚实说明的边界

- 当前跨实例广播使用的是 Redis 事件流轮询同步，不是更完整的 Pub/Sub 或 Stream 消费组。
- 结算租约已经能减少重复结算，但还可以继续增强为更完整的续租和故障恢复机制。
- 全量压测仍建议在独立压测机上执行，不建议和后端部署机混跑。
